# Decisions and deviations from the baseline plan

The baseline plan ([aws-lambda-baseline-plan.md](aws-lambda-baseline-plan.md)) is the
source of truth. Where practice differs, the difference is recorded here with the
reason, so nothing changes silently.

## Decided

| # | Decision | Reason |
|---|---|---|
| D1 | Region `us-east-1`, no custom domain | Cheapest, fewest surprises. A domain is a yearly cost and optional |
| D2 | `just` as task runner, recipes run in Git Bash | Readable showcase. The path to Git Bash is explicit, because a bare `bash` can be the WSL stub |
| D3 | Rebase-and-merge, one task per branch and pull request | Keeps the commit history as written. Each commit must pass CI on its own |
| D4 | Repo starts private and goes public at a gate | GitHub Free offers CodeQL, dependency review, secret scanning and push protection on public repositories only |
| D5 | Task 4 is split: 4a (gitleaks and checkov in CI) now, 4b (CodeQL, dependency review) at the go-public step | Follows from D4 |
| D6 | Dependabot uses the `opentofu` ecosystem, not `terraform` | GitHub added a dedicated ecosystem on 2025-12-16. `opentofu`, `docker` and `npm` entries are added in tasks 6, 11 and 12 |
| D7 | Budget and Cost Anomaly Detection are created in task 6 through OpenTofu, not by hand in task 5 | "Create nothing by hand", and they must be tagged and destroyable |
| D8 | Gitleaks runs in CI from a release pinned by SHA-256 | No third-party action needed |
| D9 | The `apply` role is created in task 8, not task 6 | It trusts the protected environment's OIDC claim, which can only be verified in task 8. It is also the most powerful role |
| D10 | The `plan` role uses a custom read-only policy for the services in use, not `ReadOnlyAccess` | Least privilege. Missing read actions show up in the first CI plan (task 8) and are added then |
| D11 | A permission boundary caps every project role: allowed services only, one region, expensive services denied | The cost-risk allowlist in IAM form. Checkov findings on the boundary are skipped with a stated reason |
| D12 | Trust policies use the immutable subject format `repo:OWNER@OWNER_ID/REPO@REPO_ID:...` | Repositories created after 2026-07-15 use it. All three contexts were verified from real tokens on 2026-10-21 (see below) |

| D13 | Local bootstrap identity is the IAM user `portfolio-admin` (MFA, no keys) with `aws login` | Temporary credentials, no stored keys. Root stays unused. Needed again for teardown and the rebuild rehearsal |
| D14 | Reserved concurrency cannot be set: the account's Lambda concurrent executions quota is 10. **Superseded by D38** | AWS requires about 100 unreserved. The quota is adjustable. The limit of 10 acts as a natural cap while it stays low. See open items |

| D15 | The repository went public on 2026-10-21, in two applies (visibility, then secret scanning and push protection) | GitHub rejects the security settings in the same update as the flip. The `enable_secret_scanning` variable controls the second step |

| D16 | Branch protection is a ruleset with no bypass actors. Break-glass is `ruleset_enforcement=disabled` applied from the laptop | The rules bind the owner too. The escape hatch is code, so it is reviewable and rehearsed |
| D17 | Only GitHub-owned actions plus an allowlist may run, and every action must be SHA-pinned (enforced by GitHub, not only by zizmor) | Supply-chain control. A new action is a reviewed change to `allowed_action_patterns` |
| D18 | Fork PR approval and private vulnerability reporting are set with `gh api` and checked by `just github-settings-check` | No provider resource exists for them |

| D19 | The AWS account ID reaches workflows as the GitHub Actions **secret** `AWS_ACCOUNT_ID`, set by OpenTofu from `TF_VAR_aws_account_id` | The role ARN needs it, and it must not appear in files or public logs. It is not a credential, but only secrets are masked by GitHub. A first version used an Actions variable on the assumption that the credentials action masks the ID. It does not: the first CI plan printed the ID in the step header and in every ARN line. That run's log was deleted, and neither the action nor an `add-mask` step can hide a variable from the step that first uses it |
| D20 | CI plans the bootstrap root with a placeholder alert email, and the Budget and anomaly subscription use `ignore_changes` | The email is personal and is not stored in GitHub. To change the email or thresholds, replace the two resources (see the bootstrap runbook). Drift on those attributes is not detected |
| D21 | The `apply` role is created in task 8 with no resource permissions, only the prod state keys | The role that deploys from the protected environment never holds more than the code in the repository needs. Task 14 adds its permissions with the code that needs them |

| D22 | The `plan` workflow runs only when `infra/bootstrap/**` changes, so it is not a required check. Its job summary shows only the plan's one-line result | A path-filtered check that does not run would block unrelated pull requests. A plan in a public summary could expose the account ID |

| D23 | The API's test client keeps the stable `httpx 0.28.1`, and pytest ignores only Starlette's one deprecation notice about it | Starlette now prefers `httpx2`, a new package from the Pydantic organisation whose newest releases are days old. Revisit when Starlette removes httpx support. All other warnings are errors |
| D24 | The API is a plain module-level `app` with the lifespan loading and validating the content, routers in their own module, a singleton content store and `uvicorn.run` under `__main__`. A missing or invalid content file aborts the start-up. Docs routes are off unless `ENABLE_DOCS=1` | This is the layout the project owner prefers for FastAPI services. A broken content build must not serve, and the lifespan is the idiomatic place for start-up work (task 21 reuses it for the database client). Typing is kept: a content store and a `get_content` dependency instead of an untyped `app.state`, so tests override the dependency or point `CONTENT_FILE` at a file. A first version used a factory function with everything nested in it: it failed fast just as well, but was harder to read and needed `--factory` |

| D25 | The running version has one source, the environment variable `APP_VERSION` (and `GIT_SHA`), set by the release build from the git tag. `pyproject.toml` keeps a placeholder, and `/health` and OpenAPI report the variable | The first version hardcoded `0.1.0` in two places that could drift, and the plan had no release mechanism at all. A test fails if a release version is hardcoded in the package |
| D26 | Releases are tag-driven (task 15a, added to the plan): a `vX.Y.Z` tag builds the image and creates a GitHub Release with generated notes. `release-please` is not used | `release-please` opens a pull request with `GITHUB_TOKEN`, which does not trigger CI, so the required checks could never pass. Making them run needs a personal token or a GitHub App key stored in GitHub, which we avoid |

| D27 | The container build, lint and smoke test are one required CI job, `image (hadolint, build, smoke)`, with no path filter. It uses plain `docker build` and `docker compose` with provenance attestations off, so no third-party Docker action is allowed or needed | A path-filtered required check would block unrelated pull requests. Lambda does not accept multi-architecture images, and provenance attestations turn the image into an OCI index. The adapter, the base image and the `uv` image are pinned by digest |
| D28 | Docker stays CI-only. WSL 2 with Docker Engine was offered (the laptop can run it) and declined by the owner. Revisit if the CI feedback loop for container work becomes too slow | Keeps the local toolchain native and small. CI is the source of truth for container behaviour either way |
| D29 | The contract between the API and the site is the JSON Schema generated from the Pydantic models (`content/schema/published.schema.json`, committed, a test fails when it is stale). The site generates its TypeScript types from that file and a test validates the embedded snapshot against it | One source of truth for the shape of the data. An API change that breaks the site fails a build instead of the live page. Hand-written types would drift |
| D30 | The site is built to be redesigned later: colours, spacing and type come from CSS variables (`tokens.css`), components are pure functions of their props and render on a server without browser globals (tested), the title, description and Content-Security-Policy in `index.html` are filled from the content at build time, and bundle size has a budget (90 KB JS, 15 KB CSS, gzipped) | The owner plans a UI/UX pass after the backend and deployment are done (Could item in the plan). These choices keep that pass from touching data loading, tests or the build. Pre-rendering and a theme switch become small changes |
| D31 | The web toolchain is pinned to exact versions with `ignore-scripts`, and ESLint stays on 9 and TypeScript on 6.0.3 for now. Dependabot ignores the next major of `typescript`, `eslint` and `@eslint/js` | The lint plugins (React hooks, accessibility, typescript-eslint) lag the newest ESLint and TypeScript majors. A broken lint setup blocks every pull request, so those jumps are deliberate tasks. Install scripts of dependencies never run on the laptop or in CI |
| D32 | Live data (task 12c): the site renders the saved copy first and swaps in the API's content if it answers within 5 s. With no API configured (`VITE_API_URL` unset in a production build) it fetches nothing and shows no status. Data from the API is checked by a complete structural guard, only `http(s)` links pass, and an error boundary falls back to the saved copy. Both requests use `cache: 'no-cache'`. The status line is at the bottom of the page | Saying "API offline" about an API that was never configured would be false. The API is not trusted: a bad response must not break the page or add a `javascript:` link. In the browser check, `/content` (cacheable for 5 minutes) was answered from the HTTP cache while the API was down and the page claimed "Live from API", so the status is made honest by revalidating. A late result at the bottom cannot move the content. Known trade-off: a cold Lambda start slower than 5 s shows "offline" while the API is fine |
| D33 | The site is published by its own workflow, `pages.yml`, on push to `main` (path-filtered to the site's inputs) and on demand. Build and deploy are separate jobs: the build has a read-only token, only the deploy job has `pages: write` and `id-token: write`. The deploy is verified by comparing the live `index.html` with the SHA-256 of the built one and loading its assets. It is not a required check and the Pages environment stays limited to `main` | Merging is the approval to publish, so a deploy needs no second gate. Keeping the write permissions in one small job limits what a compromised build step can do. A hash comparison proves the CDN serves this build, not an older cached one. The verify script was tested against a local server (match, wrong hash, wrong path). The deploy job itself cannot run before the first merge, because the environment refuses branches |
| D34 | Task 14 is split into 14a (the `infra/prod` root and the apply-role permissions), 14b (the build-and-push slice of task 15: build on `main`, push by digest through the `ecr-push` role, no scan or deploy yet) and 14c (apply the Lambda with that digest, prove it answers, rehearse destroy and recreate) | Docker runs only in CI and only the `ecr-push` role from `main` may push, so no image can exist until a workflow on `main` builds one, yet the task's "done when" needs a running function. Task 15 keeps Trivy, the approval gate and deploy by digest |
| D35 | The Lambda and its Function URL exist only while `image_digest` is set. The repository keeps the newest 3 images (not 2), tags are immutable, images are scanned on push, reserved concurrency is optional (**2 by default since D38**, it started off), and the URL is not used by the site until task 16 | The repository has to exist before an image can be pushed. With 2, two pushes before a deploy would expire the image that is running. Immutable tags mean a tag can never silently change what runs. The account's concurrency quota was 10, which allowed no reservation (it is 40 since the day of the first deploy, D38). The two public-invoke statements were added because the AWS docs call them mandatory; AWS turned out to add its own as well (D38). A public URL with no auth is the main cost-abuse path, so it stays unpublished while it is unhardened |
| D36 | The apply role gets its resource permissions in a separate policy, `apply-prod-resources`, limited to `portfolio-*` resources. Roles it creates must be named `portfolio-prod-*` and carry the permission boundary, and it has no `iam:AttachRolePolicy` and no boundary-changing action. Pull-request plans of the prod root use the digest that is deployed now. `plan.yml` now fails when a plan fails | A separate policy keeps the state-only policy readable and the change a pure addition (no replace of the existing policy). The name pattern excludes `plan`, `apply` and `ecr-push`, so the role cannot change any bootstrap role. Without the digest a PR plan would show a deployed function as about to be destroyed. The old step piped `tofu plan` into `tee` without `pipefail`, so a failed plan would not have failed the job |
| D37 | The image is built and pushed by `build.yml` after a merge to `main` (14b, the slice of task 15 pulled forward). It smoke-tests first and pushes the image that passed, tagged only `sha-<commit>`. An existing tag is reused, never rebuilt or overwritten. The ECR steps live in `scripts/ecr-image.sh`, tested with fake `aws` and `docker` commands in CI. No new third-party action: login is `aws ecr get-login-password`. The job fails on an image index or manifest list | Immutable tags forbid re-pushing a tag, and a re-run must be safe, so the job asks ECR first and treats "not found" differently from every other error (the test proves an access error is not read as "not found"). Pushing the smoke-tested image, not a second build, means what runs is what was tested. The AWS steps cannot run before the first merge (the role trusts `main` only), so their logic is covered by the fake-command tests and the first run is the real proof. The registry host contains the account ID, so it is built from the masked secret and never written to the summary |
| D38 | What the first real deploy and the destroy-and-recreate rehearsal (2026-10-22) changed. (1) Reserved concurrency defaults to **2** in the code. The account quota is 40 (the request for 1,000 is still open) and AWS kept only 10 unreserved, so the cap works. D14 is superseded. A default-quota account sets it to `null`. (2) AWS adds `FunctionURLAllowPublicAccess` and `FunctionURLAllowInvokeAction` itself when a public URL is created, so our two statements duplicate them. They stay, because the code then states the requirement. The runbook wording is corrected. (3) A cold start takes 3.9 to 4.6 s from the owner's laptop (2.8 s of init), against the site's 5 s live-data deadline. The timeout is raised or the init trimmed before the URL goes into the site (after task 16). (4) A rebuild of the same commit gives a different digest, which is why deploys use the digest. (5) The registry returned 429 for the base-image pulls in the build, twice in a row, then passed | The cap was passed as a flag at the first deploy, so it was not in the code and every pull-request plan would have shown a diff to remove it. The duplicate statements are harmless, and removing them could break the URL if AWS changes its behaviour. The cold start leaves under a second of margin, which a slow network would use up. Rebuilds are not bit-for-bit reproducible, so a tag cannot name a build. The 429 from `public.ecr.aws` also hit a pull-request check earlier, so authenticated pulls or a retry are a real follow-up, not a one-off |
| D39 | Image scanning (task 15, slice 1): Trivy v0.75.0, installed by `scripts/install-trivy.sh` with the SHA-256 of the release archive pinned in the script (cross-checked against the release's `checksums.txt`). The scan (`scripts/scan-image.sh`) runs on the smoke-tested image in the CI `image` job and in `build.yml` **before the push**. It fails on fixable HIGH or CRITICAL vulnerabilities (`--ignore-unfixed`) and on secrets. Exceptions live in `.trivyignore.yaml` and need a reason and an expiry. The vulnerability database comes from public ECR with GHCR as a fallback. The image build and the database download are retried (`scripts/retry.sh`, 3 and 4 attempts). No action, no cache | A checksum-pinned binary avoids a third-party action (the Trivy action was compromised earlier in 2026) and needs no allowlist change. Scanning before the push keeps a bad image out of ECR, and scanning in the pull request catches a vulnerable base-image bump before it breaks the post-merge build. A cache of the database would let a poisoned cache hide findings in the job that pushes, so there is none. `--ignore-unfixed` fails only on what can be fixed. The retries answer the 429 that hit the pipeline four times. The CI job keeps its name `image (hadolint, build, smoke)` because renaming a required check needs a ruleset apply, so the name no longer mentions the scan. Dependabot does not track the Trivy version, so it is updated by hand with its checksum (a task 20 item, with the other inline pins). **First real scan:** it found 5 fixable HIGH or CRITICAL findings (certifi, msgpack, setuptools, urllib3 twice) that are not in the app's dependencies but in the copies bundled inside pip in the base image. pip is not used at run time, so the Dockerfile now removes it (it also drops some size and a tool). **The retry did not outlast a 429 episode** on the first pull request (3 attempts over 90 s all failed, and a re-run failed the build step too before it passed), so retries only help a short throttle. A durable fix is authenticated pulls or mirroring the adapter image into GHCR, and is still open |
| D40 | Image pulls from `public.ecr.aws` are authenticated with the job's AWS identity. A job assumes a role through GitHub OIDC (the `plan` role in the pull-request `image` job, the `ecr-push` role in `build.yml`), runs `aws ecr-public get-login-password` and `docker login` (`scripts/ecr-public-login.sh`). Both roles get `ecr-public:GetAuthorizationToken` and `sts:GetServiceBearerToken` (with no condition, see the correction below), and the permission boundary allows only that one `ecr-public` action. The login never fails the job: without it the pull is anonymous, as before. **Decision rule:** this is an experiment. If a build that logged in (the log says "Logged in to public.ecr.aws") still fails with `429`, in about the next ten builds, move to vendoring the adapter binary into the repository (option 1), which removes the registry from the build | The adapter image is the one pull that failed: the anonymous limit of public ECR is shared by every GitHub runner and was exhausted for minutes at a time, and a retry cannot outlast that. AWS documents higher limits for authenticated pulls. It uses the same OIDC trust as the other jobs, so there are no stored credentials. The token cannot push to a public registry (no other `ecr-public` action is granted anywhere, and a test says so). Making the login non-fatal means a problem with AWS cannot break the build, only leave it as flaky as before. The byte-based limit behind the "Data limit exceeded" message is not documented for authenticated pulls, which is why the outcome is measured and the vendoring fallback is decided in advance. Fork pull requests get no OIDC token and stay anonymous. **Correction after the first real run:** the version applied first limited `sts:GetServiceBearerToken` with `sts:AWSServiceName = ecr-public.amazonaws.com`, and AWS refused the login ("no identity-based policy allows" the action), because ECR Public makes that STS call itself and the condition did not match. The condition is removed, as in the AWS documentation's policy. The action alone gets nothing (a token also needs the service's own `GetAuthorizationToken` permission, and ECR Public's is the only one any role has, which a test checks). The login's soft failure did its job: the build carried on anonymously and the warning named the exact denied action |
| D41 | Deploy by digest (task 15, slice 2). `build.yml` calls `deploy.yml` after every push of an image; `deploy.yml` can also be run by hand with a digest, which is the rollback, and has a dry-run option. The job waits for the owner's approval in the `prod` environment, then assumes the `apply` role, plans with `-var image_digest=<digest>`, and applies **only** a plan that `scripts/check_deploy_plan.py` accepts: an in-place update of `aws_lambda_function.api[0]` that changes nothing but `image_uri`, which must end in the approved digest. It then applies that exact saved plan and checks `/health` for the image's commit (`scripts/verify_deploy.py`, with the commit read from the image's `sha-<commit>` tag by `scripts/image-commit.sh`). Zizmor's `self-repository` finding is ignored for `build.yml` because actionlint rejects the `$/` syntax it asks for | A deploy by digest should never be able to destroy or reconfigure anything, whatever is in the plan, so the guard checks the plan and not just the intent. Applying the saved plan means what was checked is what runs. The approval comes before the plan is visible, because the read-only plan role only works on pull requests: the dry run and the safety check make up for it. Every merge that changes the image now creates a pending approval, and nothing deploys unattended. Python, standard library only, so the checks run on the plain runner and are tested locally with fake plans and a local server. The first real run may find a missing read permission on the `apply` role, which fails before any change. **First real run (2026-10-24):** the dry run passed with no permission gaps and the real deploy applied one change and verified `/health` |
| D42 | Releases (task 15a). A tag `vX.Y.Z` starts `release-tag.yml`, which has no AWS access, checks the tag (plain x.y.z, points at the commit, commit on `main`: `scripts/check-release.sh`) and starts `release.yml` **from `main`**. `release.yml` repeats the check, builds the commit with `APP_VERSION=x.y.z` through the shared `image.yml` (the same smoke test, scan and push as every image), tags it `vX.Y.Z` and `sha-<commit>-vX.Y.Z`, creates the GitHub Release (`--verify-tag`, generated notes, image digest), and offers the image for deployment. `build.yml` now calls the same `image.yml`. The deploy reads commit **and version** from the image tags and the post-deploy check requires both. The release tag is added to the same image with its manifest (`put-image`), so a run that stopped between two tags can be repeated. `release-please` is still not used (D26) | The plan's done-when is that a pushed tag produces a release whose image reports that version and commit. A job run from a tag would need the image-push role to trust any tag, and a tag can point at any commit with any workflow, which would give up the rule that only reviewed code on `main` gets AWS credentials (D40 relies on it too). Splitting the trigger from the privileged part keeps that rule and needs no bootstrap change. One reusable `image.yml` keeps the two builds from drifting apart. Only a commit on `main` can be released. Tags are immutable in ECR, so re-running a release reuses the images and never overwrites a tag. The real path (a tag, the dispatch and the release) cannot run before the merge, so its logic is covered by tests with a real temporary git repository and fake `aws` commands, and the first tag is the proof. **First release (2026-10-24):** v0.1.0 went through the whole path (tag, dispatch from `main`, image, GitHub Release, approved deploy) and `/health` reported 0.1.0 and the commit |
| D43 | API hardening (task 16). The API is read-only: it refuses methods other than `GET` and `OPTIONS` (405), any request body (413), more than 16 KB of headers (431) and a URL over 2048 bytes (414), in a middleware that runs first. Every response carries security headers (`nosniff`, a `default-src 'none'` CSP, `no-referrer`, `X-Frame-Options`, HSTS) and is `no-store` unless it sets its own cache header. CORS allows exactly one origin, the site on GitHub Pages, for `GET` and `OPTIONS`, with no credentials and no wildcard, configured by `CORS_ALLOW_ORIGINS`, which is **baked into the image** and validated at start-up. Without the variable there are no CORS headers. The smoke test checks all of it against the real container, plus that the image has no secret-looking variable or file | The origin is public and fixed, and an environment variable on the Lambda would be a non-image change that the deploy safety check (D41) rightly refuses, so the deploy stays an image swap. Checking sizes in our own middleware was needed because uvicorn's header limit only applies to a request that arrives in pieces: running the checks against the real server showed a 20 KB header was accepted. CORS is not access control (curl ignores it), so the docs say what really bounds abuse: the concurrency cap of 2, the no-body rule and the budget alert. Connecting the site to the live URL, with a longer live-data deadline for the 4 to 5 s cold start and a check in a real browser, is a separate step (16b) |
| D44 | Connecting the site to the API (task 16b). The production build reads `VITE_API_URL` from a committed file, `web/.env.production` (an exception in `.gitignore`). The live-data deadline is **8 s** (D32 said 5 s), and the site asks for `/health` only after `/content` has answered. `npm run check:page` (CI web job and `pages.yml`) fails if the bundle or the page's `connect-src` does not match the file. Checked in a real browser from the site's own origin: `fetch` with `cache: 'no-cache'` and `Accept` reads `/content` and `/health` with CORS, and a request with another header is blocked | The address is public anyway (page JavaScript, CSP), so a file in the repository costs nothing and gives a reviewed change and an identical local and CI build, which an Actions variable (set outside review) would not. It must be updated by pull request when the function is recreated, until then the site shows the saved copy, which is the designed fallback. A cold start of 4 to 5 s left under a second of margin against 5 s, and the saved copy is already on screen, so a longer deadline only delays the label. The function allows two concurrent executions: two requests at once on a cold start would use both for one visitor, so they run in sequence (the second is warm, about 100 ms). The browser check could not run from GitHub's 404 page, which has its own CSP, so it ran from a script file served on the site's origin. A later check (task 17) can compare the file with `tofu output function_url` |
| D45 | End-to-end test of the site against the API (task 17). A new required job, `e2e (stack, site)`, starts the container (Compose with `docker-compose.e2e.yml`, which only adds the test site's origin to CORS) and runs `web/e2e` with Playwright 1.64.1 in the runner's own Google Chrome. The empty `<link rel="icon" href="data:,">` was added because the test found a console error: the browser asked for `/favicon.ico` and got a 404 | The unit tests use a fake `fetch`, so none of them could see a CSP, CORS or cache problem: those were found by hand in tasks 12c and 16b. The failure modes use Playwright's request interception because they do not need the container, which keeps the real-stack part to the happy path. A separate required job (not steps in the image job) keeps the check names honest; adding it needed one `infra/github` apply |
| D46 | Standing checks of the deployed system (task 17, part 2). `scripts/check_live.py` (standard library, unit-tested against a fake site and API) is run daily and on demand by `synthetic.yml` with no credentials. It takes the API address from the live site's own policy, then checks health and version, content, CORS for the site and for a stranger, security headers and that a write is refused, with 3 attempts 20 s apart. `deploy.yml` ends with a step that compares `web/.env.production` with `tofu output function_url` (`scripts/check-site-link.sh`, tested). The workflow is not a required check and opens no issues | Everything before this proves a commit, an image or a deploy. Nothing noticed an API that went down later, a platform change, or a site left calling a recreated function's old address (a recreate happens outside `deploy.yml`, so only the daily run sees it). Reading the address from the site checks what visitors really get instead of what the repository says. A Lambda platform banner is allowed: only our own `uvicorn` banner is a leak. A failed scheduled run is emailed by GitHub to whoever last edited the schedule; automatic issues would be outward-facing noise for one maintainer. The deploy step comes last so a red mark means "the site calls another address", not "the deploy failed" |
| D47 | Cost guards verified (task 18). The emergency brake was applied and released for real, and the cap was shown to throttle under a burst (see the runbook table). The alert path is tested with `budget_alert_test`, a second $0.01 budget in the bootstrap root that is off by default and removed after the email arrives. `check_live.py` no longer counts "nothing to look at" as a pass for the approval-state and stranger-CORS checks | An untested brake is a hope. The two applies were small and shown in full first. Testing the alert with a temporary budget leaves the real $1 Budget and its thresholds alone (changing the real one for the test would weaken the guard during it), costs nothing (plain budgets are free) and is repeatable from the code.
